# Unresolved questions

- **Launcher/model contract:** publish the jointly accepted string configuration
  and launcher-to-host/runner plan ownership, including where current manager
  admission is enforced. No second registry or unilateral payload extension.
- **Process proof/home lease:** qualify the session-record revision and kernel
  process-incarnation evidence required to complete hosted admission. The M1
  public runner instance identifier is not that proof. Exact-plan compatibility
  and successful lease binding remain unimplemented.
- **Real harness qualification:** Codex protocol and owned test-session behavior
  follow the fixture milestone; Claude Code is the next adapter. Human input,
  approval handling and real idle/turn semantics need separate qualification.
- **Production control security:** kernel UID checks in M1 authenticate an OS
  user, not agents sharing that user. Admit session/caller-scoped capabilities
  and cross-UID qualification before real deployment. No credential provisioning
  is part of M1.
- **CI qualification:** verify the hosted module-wide `go vet` and `go test`
  results for the exact prototype revision after the separate workflow change.
  No private source checkout is a dependency of the new host.
- **Repository settings:** existing credentials remain under repository-owner
  custody. Any change requires the owner's separate decision; product
  development does not read, export or modify their values.
- **Later features:** optional goals and their namespace/authority, migration,
  detector automation, process-tree confinement, service installation and other
  platform backends remain separate work; none is activated by M1.
