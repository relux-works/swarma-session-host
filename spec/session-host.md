## 1. What the host is

The session host keeps agent sessions alive in the background: it starts a harness in a given directory, lets a person attach and detach, delivers messages into a session, and reports events. A goal is optional. The module MUST work without goals, a board, an orchestrator or their toolchain. Task-board is an OPTIONAL client of a generic goal interface (§3.8). Today this is `tb-sessiond`, the session manager inside task-board (`tools/board-cli/internal/sessionmanager` in relux-works/skill-project-management).

| Phase | Service and logical ownership | Process ownership |
|---|---|---|
| Today / SH1 extraction | Board-composed `tb-sessiond`; the extracted module supplies its serving library through C1 | The daemon owns Claude's PTY master and a private Codex app-server per session |
| SH2+ target, after activation | `swarma-session-host` owns durable metadata, logs, receipts, fences and input admission; `swarma-dispatcher` owns admission, allocation, execution records and cleanup | One `swarma-session-runner` per session under `worker-<label>` owns its PTY master or private app-server transport and credential lease client |

Logical ownership by the host module does not mean that the service account owns the harness or its transport. The agent account generation, execution identity and host controller epoch are separate (§3.3).

[M-SH1 logical components](../diagrams/components.puml) distinguish current/SH1
from the gated SH2+ target. The component view groups specified responsibilities;
it does not define new internal APIs.

### 1.1 Today *(fact, at the pinned source)*

- One control plane per board, keyed by `BoardKey`; state in the user state directory; self-restoring start-up; one daemon per board.
- The daemon registers Claude (a PTY the daemon owns), Codex (a private app-server per session) and Muse PTY provider factories. Codex goals are delivered as text directives; its native goals are disabled.
- At skill-project-management `077e000e6`, `musepty.NewMusePTYHostFactory` is registered in production (`cmd/tb-sessiond/main.go:142` and `boardless.go:35`); only the MSP `MuseHostFactory` is unregistered. The hosted launch route decodes its input and always refuses capability admission.
- Goals are applied inside the board's write transaction; Claude acknowledges the exact rendered revision; deferred application has an acknowledgement waiter.
- Notices: a durable inbox per session, written directly by board producers, delivered only while a client is attached.
- A Claude session dies when the daemon is replaced (the daemon holds the PTY master).
- Access control: one bearer token in a private file; any process of the operator's user can use it.

Denial tests are bound to the production path across the converters.

Provider success means exactly what it means today: Claude's exact acknowledgement and deferral; Codex's text directives; Muse's accepted adapter behaviour (PTY factory registered, MSP factory unregistered).

### 2.6 Cutover (C1)

Figure: [M-SH4 gate and operator cutover](../diagrams/sh1-gate-deployment.puml)
includes quiescence refusal and schema-safe rollback.

- Not before the board's conference window ends (19 October).
- **Quiescence for the whole transaction.** Before stopping the daemon, the operator closes every entry path for the affected boards: the wrappers' automatic daemon start, scheduled and recovery starts, active board runners and operator entry points, using the host's existing maintenance controls. Exclusive state ownership is held and re-checked through snapshot, binary swap, start and health verification. If quiescence cannot be established, cutover is deferred.
- A paired release manifest names the board build, the module tag, the wire, goal and storage schema versions, and the permitted reader and writer pairs; the board build stamp stays in the daemon version, the host identity is reported separately.
- The operator performs the swap inside a maintenance slot; the replacement guard stays; the system reopens only with the paired identity and one verified writer.
- Disposable acceptance covers late starts by old clients and all four old/new wrapper and daemon pairings.
- Rollback opens mutable state only after proving the old reader accepts every retained schema, and never erases later records by restoring an old snapshot.

## 3. Phase SH2+: platform canons

Each item below is an **activation gate**: it is designed and tested before it is switched on, and SH1's unchanged tests are not evidence for it.

### 3.1 Service account, state and capabilities

Figures: [M-SH1 process ownership](../diagrams/containers.puml) and
[M-SH4 storage ownership](../diagrams/storage-layout.puml) show service-private
state, agent-side transports and the authenticated socket boundary.

- The host moves to its own service account `swarma-session-host` (home `/opt/swarma/services/swarma-session-host`) only after the direct file APIs (notice inbox writes, context-state reads by the board) are replaced by authenticated calls, and only together with agent-account session runners (§3.2). Running harnesses as the service account is not a boundary.
- The socket directory `/opt/swarma/run/session-host/` has published permissions that let authorised principals connect while the data stays private. Connections follow broker §4.1: kernel peer UID, server identity check, close-on-exec, one role per connection; managed principals by `(uid, generation)`.
- Account generations are fresh random 128-bit values (R-GEN). Active managed generations are checked against the user manager's root-owned ledger, by default `/opt/swarma/lib/user-manager/ledger.json`. Readability is not authority; a malformed, unreadable, ambiguous or retired record is not an absent identity and cannot authorise a fallback.
- **Ledger loss and restore (F-17/R-GEN).** Follow the user manager's state-loss/restore procedure (§§4.1, 4.5–4.6, §14) and the dispatcher's (§§4.6, 7.1, 11). The shared operator restore fence closes every ledger consumer, including the host, before restored bytes become visible. The host durably records the highest ledger store epoch it has observed and refuses a lower epoch until operator reconciliation. A reader's epoch floor helps only while its evidence survives outside the restored failure domain; it does not replace the restore fence or coverage proof, nor detect an internally consistent whole-machine rollback. Lost or incomplete evidence is unknown, not absence, and cannot reopen delivery or successor admission. A retired generation MUST NOT be revived by restore.
- **Service egress (F-24/R-SVC-EGRESS).** The host service account has deny-all network egress, including loopback TCP; platform calls use Unix sockets. The user manager's §8 owns the v1 service-profile row, parent-anchor checks, resolver sandbox qualification, start-time verification and scheduled re-verification with its published owner. Per-UID packet denial alone does not prove DNS denial through a system resolver. Host readiness requires the verified deny-all row, parent anchor and qualified resolver restriction. A missing or invalid row drops readiness and raises an incident; recovery controls follow F-15 and process response follows R-FATE, without interpreting missing policy as permission. Periodic checks leave a detection window; continuous enforcement is not claimed. Service-profile and per-OS evidence remain activation gates (§7).
- **Credential renewal (F-14/R-REBIND).** Standing-session lifetime does not extend credential authority. Follow dispatcher E-rebind (§§3.4–3.5, 5.2, 7.1–7.2) and broker binding replacement (§§7.1–7.3, 8.3, 8.5): the same `(uid, generation)` is retained, the leaf is re-signed under current chains, the old binding has a removal tombstone, and each rebind uses a fresh `revocation.check` with context `prepare`. The renewing principal must already be in the chain; authority never widens and the account is not re-created. Pending or expired renewal keeps dependent readiness, leases and restarts closed; an env-channel token already issued is not withdrawn by replacing the binding. A revoked envelope or key requires an explicit operator decision, never automatic renewal.
- **Time confidence (F-21/R-TIME).** The installer requires an authenticated or operator-controlled time source, for example NTS, as specified by the user manager's installer and the dispatcher/broker time contracts. Their durable time watermark checks expiry at `max(now, watermark)` and `not_before` at `min(now, watermark)`; it never advances on untrusted time and its reset is an explicit operator act. Clock steps can only narrow authority. Expiry-driven home deletion or binding removal also needs boot-inclusive monotonic elapsed time of at least the lifetime; it is not triggered by the host's liveness deadline. The host follows the shared time-confidence hold policy: untrusted time cannot justify successor admission or revive expired session authority; explicit authorised stops remain available.
- **Cross-account workspace (F-16/R-TRANSFER).** Materialization and export belong to the **dispatcher’s workspace contract**, never a launcher contract. The caller supplies admitted exact base B (a commit of the caller’s repository) as a bounded canonical archive of B’s tree with the start request; the dispatcher holds no repository, relays the archive and journals its digest. Approved executor `swarma-workspace-materialize` runs as the child UID before work, writing a standalone repository in the private home with freshly written local configuration, no hooks, no remotes and no credential helpers. No linked `git worktree` or administrative backlink crosses accounts; same-account worktrees and today’s board workflow stay. The digested launch plan covers B, the file-manifest digest (each path maps to supported Git kind/mode and content identity), task **write scope** and the machine-selected R-EXEC profile identity/policy digest. The immutable manifest is bound to exact B and remains available to the exporter; its encoding and custody are publication prerequisites. Validators stay outside that scope unless the task is about them; light-check dependencies come only from platform-seeded read-only caches. Archive and exact plan formats are unpublished (§7.13).
- **Workspace round boundary (R-TRANSFER).** Worker `.git`, commits and history are never platform inputs. A local board outcome or remote signed final envelope proposes round end; account-wide process absence must be confirmed before `swarma-workspace-export` runs as the child UID with a fixed environment and no network. A workplace’s round workspace is also write-fenced by its project-side executor. Export compares both mode and content identity against the immutable admitted manifest without following links or using any `.git` component: mode-only edits and equal-blob regular-file/symlink transitions are modifications, and deletions carry the manifest’s prior mode. It emits changed regular-file content/executable bits, symlink text and deleted paths. File-count, per-file, total and binary caps apply; special files, `.git` paths however spelled, case-fold/Unicode-normalisation collisions, gitlinks/submodules, root escapes or cap excess refuse the whole export with no partial result. The approved exporter digest and cap values are pinned by the plan digest; the walk stops at the first cap excess. Caps, walk order and operation refusal codes remain unpublished. The dispatcher owns the [DRAFT result object and schema](https://github.com/relux-works/swarma-dispatcher/blob/74687e600e04817fa6e7a2e8904a9f7a3c83a1d8/spec/dispatcher.md#521-draft-swarma-dispatcher-workspace-result1); published draft bytes do not establish transport, retention or activation (§7.13). The dispatcher journals result digests and releases data only to the authenticated original caller principal. The host adds no transfer authority.
- **Export outcomes and repair (R-TRANSFER).** Recorded export, deterministic policy refusal, interrupted/unknown export and authorised discard are distinct lifecycle outcomes, not new result fields. A terminal export effect replays its retained result; a new linked observation cannot replace it. Contradiction compares the outcome class or recorded change-set digest, not walk-dependent refusal diagnostics. A refusal retains the cleanup obligation, home, UID reservation and live-allocation claim; execution capacity releases only on confirmed absence. The original caller may request plan-bounded fix-up turns on the same workspace only under current work authority and a separately admitted continuation. Each repair is a new fenced round with distinct linked work/export evidence; workplace write and ingress fences reopen only for admitted repair, then close through quiescence and export. The worker receives only refusal class/path in a letter or task snapshot, never a partial change set. A repaired export is whole, with account-wide absence checked again. Exhausted budget or expired/revoked work authority retains the obligation pending a per-act operator waiver; automatic standing discard is unchosen and off. A known permission denial on a source entry in the qualified exporter environment needs a bounded typed failure/disposition with the same repair path; its format is unpublished and no result refusal class is added here. Infrastructure denial, I/O failure or ambiguous identity remains pending/unknown. The exporter neither changes permissions nor raises privilege. Refusal produces no candidate C: continue by an admitted repair round, or, after authorised disposition, by a new admitted round on the last admitted base (§7.13).
- **Cleanup export authority and custody (R-TRANSFER).** Original workspace admission explicitly consents to bounded continuation of its durable export obligation after ordinary caller or allocation expiry, tied to the exact generation/round, approved exporter and immutable base/manifest/scope. It grants no harness, lease, network, task, repair or ordinary successor authority. Dispatcher/user-manager publication must separately define revocation, compromise, R-ALLSTOP, maintenance and restore holds; retained obligation is no bypass, and invalid cleanup authority requires an explicit operator export/recovery or waiver. Export runs before `retiring`, never under an R-SESSION permit. Materialize, work and export each have distinct execution claims, launch/stop effects, root receipts and confirmed absence, linked to the immutable round; ambiguous starts reconcile their original evidence without duplicate launch. Bounded cleanup capacity must progress alongside forward work while retaining resource/storage accounting and security fences. Deletion waits until the result and every referenced blob are digest/size-verified and durable outside the child home and retirement deletion path, with a journaled complete-content receipt, or an explicit operator waiver. Digest-only or incomplete evidence never discharges the obligation. Content remains under bounded storage accounting until authenticated import acknowledgement or another explicit authorised release; result retrieval is separately authenticated and archived caller authority cannot release data to a revoked requester. Home retirement need not wait for import once complete content survives independently (§7.13).
- **Admission class (R-UNTRUSTED/R-STANDING).** Class is recorded at registration or admission, never inferred from account names. Remote workers are untrusted-class first, every `workplace` allocation is untrusted-class unless the operator admits that remote worker to the trusted circle by an operator act, and the operator may classify further identities. The trusted circle comprises our own agents and those explicitly admitted remote workers; membership enables only donor-side opt-ins such as web search. It never relaxes zero workplace egress, the exec profile, transfer or review boundaries on our host, reviewer eligibility or host-loop eligibility. Membership, placement and enforcement class are separate facts: membership is the per-identity operator record for enumerated donor-side opt-ins; placement is a local agent account or a `workplace`, recorded at allocation; enforcement class drives ceilings, egress, exec, binding/lease refusal, deployment isolation and watcher thresholds. The existing class exception above stays unchanged. A remote identity receives only a workplace placement, even after circle admission; its loop stays at the donor and no harness binary is executable in that placement. A host session with an agent loop, including a standing session, requires both trusted class and local agent placement, plus the admitted launch authority; membership alone supplies neither placement nor authority. Review requires the positive role/placement predicates in §3.5, never just exclusion from the untrusted class. Slice 0 and user-manager v0 refuse untrusted-class admission; the refusal code is unpublished. Admission requires zero workplace egress, qualified R-CEILINGS minimums, R-EXEC, no broker subscription binding or lease ever, no local agent loop and R-SHARED. R-WORKPLACE keeps `swarma-rb-exec` under a service principal, never the workplace UID; `swarma-rb/1` and `swarma-workplace-exec/1` remain unpublished.
- **Account egress (R-NET-TOOL).** Agent and workplace accounts have no general internet, push or merge-request access. Local trusted agents reach only model-provider endpoints through their bound profile proxy with vendor names allowlisted. Workplaces have zero egress, no proxy destination and denied loopback: Linux uses a qualified per-execution namespace without external interfaces and Unix-only address families; macOS uses a qualified deny-network sandbox plus per-UID deny. No `direct` or `external-http-proxy` profile can be bound to any account, trusted or untrusted, on a platform host: direct is unbounded and an external proxy cannot show served-policy evidence. They and cooperative profiles remain for operator machines without the platform. Dependency downloads occur only in R-VERIFY runners under their controlled egress. N15 owns one profile-bound proxy listener per account generation, own-port-only account rules and attributable caps/logs. Model proxy and verification dependency egress require host/port allowlists excluding mail ports, private/metadata dial guards, per-identity rate/connection/daily-volume caps and logs; RWP’s egress service is a candidate implementation. This host references the network-profiles N15 revision, not a new proxy specification.
- **Web default-off (R-NET-TOOL 4).** The design works without web access. By default the donor’s loop reaches only its model-provider endpoints and our host, and our environment has no internet. No search or fetch tool is offered to any agent by default: CIP-0008 lockdown keeps provider-side search disabled and no donor-side web server runs. Web content mixes outside context with the environment’s context and invites injection.
- **Task resources (R-NET-TOOL 4a).** The trusted side gathers fresh documentation, API references, specifications and examples and attaches them to the task as board resources; remote workers also receive them as attachments of the signed task letter. The platform materializes these resources read-only next to the workspace, with their digests in the plan. They are data, never instructions. A worker needing more asks through an ordinary letter or outcome; the trusted side fetches, checks and attaches, and the worker never fetches. Caps and formats are unpublished (§7.14).
- **Trusted-circle web opt-in (R-NET-TOOL 4b).** Web tools are granted explicitly per identity, only within the trusted circle, never by default or to the untrusted class. Membership leaves every host boundary unchanged. The design options have unpublished formats: **(a)** qualified provider-side search that executes at the provider and adds no local fetch; remote workers require a CIP-0008 tuple change; **(b)** platform-shipped donor-side MCP server `swarma-web` for remote workers; **(c)** a local platform web-tool service over a Unix socket with its key in a service account, never an agent account, and an allowlist, rate limits and logs. The donor-side MCP server runs under its own identity in variant B or its own sandbox profile in variant C, never in the harness identity (provider allowlist only) or bridge identity, with egress only to search-provider API endpoints. It holds the donor’s own search key in that identity, or the donor’s Keychain/0600 file in variant A. Donor consent occurs at `init`. It calls search-provider APIs only, never arbitrary fetch from the donor’s address; the key never crosses the channel, appears in a `swarma-rb/1` frame or package, or becomes requestable by the project. Results reach only the donor model as tool results (§7.14).
- **Qualified host admission (R-CEILINGS).** The dispatcher checks each host’s published capability matrix per OS release against the class minimums. CPU, memory, process count, IO, disk, temporary areas, process visibility and network rows say hard/kernel, soft/watcher or absent. No OS is excluded by name. Untrusted minimums require hard process count, zero or provider-only egress, an exec profile, isolated temporary areas and hard memory/CPU/disk where provided. Acceptance of soft substitutes on a host lacking hard rows would need an operator act per host; that owner decision is open. Linux selects the root-created, non-delegated per-execution unit (R-FATE), with CPU/memory/task/IO limits, CPU-time budget, private temporary area, no new privileges, read-only system, per-UID filesystem quota, `KillUserProcesses=yes`, `/proc` `hidepid=2`, exec allowlist and qualified network isolation. macOS qualification records sandbox exec/files/network, per-user process-count and per-process CPU limits, background scheduling, aggregate APFS agents-root quota and soft watcher memory/per-account disk; no public hard per-account memory, no APFS per-user quota and the deprecated sandbox interface remain qualification gaps. Linux untrusted hosts also verify infrastructure-installed kernel baseline: disabled unprivileged user namespaces, io_uring and unprivileged eBPF, `kernel.yama.ptrace_scope=2` and timely sudo patching. Matrix formats, class values and qualification evidence remain unpublished (§7.14).
- **Range and socket readiness (R-RANGE-DENY/R-SOCKETS/R-SHARED).** The installer puts static default deny for agent/workplace UIDs 30000–59999 in the helper-owned parent anchor/table before accounts exist, independently of `fw.apply`. From v0 only platform proxy listeners are admitted; v1 narrows to the bound profile or zero egress, and untrusted requires v1. Linux uses all-protocol nftables `meta skuid` range rules with counters/logging; macOS uses pf `user` range rules plus launcher sandbox for other traffic. A dedicated test UID actively proves no earlier `quick` rule in any anchor, including ingress, matches range traffic on any interface, including loopback/tunnels, at install, every service start and the verification schedule; failure is an incident and enforced readiness drops. A test-UID socket probe must show reachable Unix sockets equal the declared platform set, with container runtimes, tailnet daemon, other users’ session daemons and every other socket unreachable. Hosts admitting untrusted work run no shared message, ingress/reverse-proxy, media or operator session-daemon services; platform services themselves are not shared services. These are host qualification/deployment prerequisites, not capabilities inferred from SH1.
- **Host-owned storage budgets (SH2+).** Agent-home ceilings do not charge service-owned bytes induced by a producer. Before durable acceptance, the host MUST attribute and reserve/charge retained output, queued input and required evidence against byte and count budgets per logical session and producer principal, and an aggregate service budget. Retained debt survives execution/session replacement and retirement until safe authorised disposition; a new live-session counter cannot erase it. Producer output MUST NOT consume a hard control/journal reserve sized for bounded admitted records and required stop, park, fence, reconciliation and audit transitions. Admission refuses if the necessary reserve cannot be maintained (§§3.2–3.4, 3.7; §7.20). Formats, values and retention policy are unpublished; no standing-session lifetime is introduced.
- Capabilities: issued by the host to a logical session and its execution, with audience, actions, expiry and revocation; parent and child relationships are authoritative host records; replacement rotates execution-scoped authority; controller epochs are reconciled before effects. The legacy global token is refused after activation. Trusted audit and transcript evidence lives at the service boundary, not in agent-writable files.
- Trusted-class standing sessions held by the host — the orchestrator and standing team members, including other orchestrators and standing agents — MUST have no preset lifetime or runtime limit (§3.5). Capability expiry bounds authority; it does not impose a standing-session lifetime. Operator maintenance uses the dispatcher's bounded maintenance stop (R-MAINT, §3.5).

### 3.2 Holders under agent accounts and the process tree

Figures: [M-SH1 containers](../diagrams/containers.puml),
[M-SH1 components](../diagrams/components.puml) and
[M-SH2 recovery sequence](../diagrams/session-recovery.puml) show runner
ownership, re-authentication, confirmed absence and privileged launch ordering.

Before session runners are activated, the ownership table is frozen:

| Concern | Owner |
|---|---|
| the PTY master or app-server transport | the session runner `swarma-session-runner`, one process per session, started only by the dispatcher through `swarma-user-launcher` under the agent account |
| the credential lease client (renewals for Codex app-server) | the same agent-side session runner, for the whole execution |
| durable metadata, logs, receipts and producer-induced retained-byte accounting / protected reserve | the host service |
| admission, allocation and execution records, cleanup | the dispatcher |
| stop | the host requests `host_stop`; the dispatcher owns the journaled E-stop path through the user manager's `exec.stop` (confirmed process absence required) |

The runner binary belongs to the session-host repository. **R-EXEC:** only the executor of the admitted plan starts the harness; the runner starts only that admitted harness, never arbitrary commands or a worker-selected agent environment. Codex has a private app-server per session under the agent UID, with no shared service-account app-server or credential pool. The runner renews its execution's credential lease; only the broker's auth owner refreshes the rotating Codex account. Broker-mode Codex uses an external access token and account ID, without copying `auth.json` into the launch home or using `codex exec`. Supported provider releases still require qualification (§7). The broker's default renewal deadline is 8 seconds; a timeout fails the turn, with no late reply or native-auth fallback. Claude setup-token has no refresh.

**Output handoff (SH2+).** The dispatcher’s existing bounded executor-output invariant MUST survive the backend handoff to the host. Runner transport buffers are bounded; the host reserves/charges bytes before retaining output, including transcript and audit overhead. Backpressure/refusal at the producer budget boundary precedes shared-store exhaustion. An uncooperative runner cannot turn backpressure into unbounded buffering or refusal logging: hold delivery closed and use the existing journaled park/`host_stop` path with reserved transition capacity. Required ordering, buffer bounds and non-cooperation behavior must be published and qualified before activation (§7.20); no direct host kill authority is added.

D-EXECUTOR makes agent-side `curator-run` the first broker consumer. The board runner and session host ask the dispatcher rather than embedding a broker client. In the versioned one-shot mode, `curator-run` under the agent account MUST only verify and execute an immutable plan composed by the caller; it MUST NOT compose or resolve profiles and has no general network access; broker calls use the admitted Unix socket and harness provider traffic follows R-NET-TOOL. It shares one launch library with `swarma-session-runner`. A separate minimal executor binary is a later option, not the current choice; the exact versioned intake remains owned by the launcher specification.

**Exec profile selection (R-EXEC; protected machine policy beside R-NETBIND).** The user manager owns the protected selection relation: admitted Curator profile identity and lock digest, intersected with placement and admission-class minimums, map to one exec-profile identity and policy digest. Caller text and caller-home configuration are never authority; no grant dimension or separate service is added. At `prepare` the dispatcher resolves the relation, refuses a reference outside its bound and pins the resolved identity/body digest in `input/1`, covered by the plan digest. At every start the launcher verifies and applies that pinned policy alongside the existing generation, class, host-matrix and qualification checks. Drift refuses rather than substituting a policy; retry/recovery use the same pin. Workplaces get the narrowest entry by default; an interpreter-bearing profile requires an explicit per-placement entry. Selection, digest and refusal encodings remain unpublished (§7.15).

**Exec profile (R-EXEC).** Each task class has an OS-enforced executable allowlist, never PATH alone: Linux makes all paths non-executable except the allowlist in the per-execution unit; macOS restricts execution with a sandbox profile. Writable areas are never executable. All agent classes exclude compilers, linkers, transpilers, bundlers, test runners, package managers/installers, container/VM tools, network tools and self-started harness/agent binaries. The plan executor’s admitted harness start is the sole harness path. Profiles may allow editing, local version-control inspection, search and qualified light checks such as type checking; interpreters only where needed. If light and heavy forms share a binary, only a protected wrapper in the D-PATH manager dispatcher directory can invoke it with a fixed subcommand allowlist; qualification must prove heavy forms refuse. Qualification covers the complete invocation: executable, fixed entrypoint/arguments, constrained environment and transitive interpreted inputs. Candidate bytes may be inspected inertly, but readable scripts, inline evaluation, imports, plugins, startup files and executable configuration must not select or supply executable behaviour locally. Protected configuration and disabled or pinned code loading must establish that boundary; an executable allowlist, non-executable writable area or fixed subcommand alone does not. Direct and indirect access to shared heavy forms must refuse, including wrapper bypass. Negative qualification exercises the real tool path for each of those inputs and environment injection, with positive controls for inert light checks. A tool that cannot prove the boundary is refused locally and routed to R-VERIFY. Ceilings bound resource use, not input inertness. `agent-headless-build` is withdrawn for agent accounts. Compilation, transpilation, tests and any worker-produced code execution belong only to R-VERIFY (§3.5), never to the session account.

- The freshly started runner opens a fresh authenticated channel to the host after the UID change, compatible with the launcher's descriptor rules (plan on descriptor 3, nothing else inherited). Registration for the admitted execution in the current controller epoch and readiness MUST precede delivery; a replacement host re-authenticates and re-adopts a live runner only after reconciliation.
- The root launcher validates the active owned generation, approved executor path/digest and home, resets descriptors and environment, and writes the atomic start receipt before clearing groups, setting GID/UID and executing. Descriptor 3 carries only the plan; no broker connection is inherited. The runner opens its broker connection after the UID change; the authenticated host channel must be established without inheriting another descriptor (§7).
- **Process fate (F-18/R-FATE).** The user manager’s §7 owns the per-process-class **fate table**, beside R-FD3. Runner roots and descendants, host-service replacement, dispatcher supervisors and broker children follow its published service-manager/kill-domain rows, stop/crash/restart fates, observation rules and R-MAINT affected execution sets. A live runner is re-adopted only when the backend promises and qualifies survival; `setsid` and UID change alone do not prove containment or survival. Every supervisor write is fenced by the durable dispatcher daemon-instance epoch; a supervisor left over from a replaced daemon is never a live adopted writer. Platform services and their service managers end executions only through `exec.stop`, retirement or operator emergency stop; OS failures such as OOM remain possible and are recorded as `lost`. Publication and per-platform qualification are required before claiming runner survival (§7).
- Dispatcher recovery distinguishes an absent controller, a live authenticated session runner, an absent execution and unknown evidence; only confirmed absence permits replacement or cleanup. Controller-only re-adoption keeps the execution id; a new exec gets a new one.
- Start, readiness and exit receipts are acknowledged and replayable; capacity release follows confirmed absence.

### 3.3 Backend activation with the dispatcher and the user manager

Enabled only with jointly pinned host, dispatcher and user-manager versions:

- `host_start` in `dispatch-op/1` (R-START/R-SESSION), accepted only from the configured session-host service principal, carrying `(logical_session_id, execution_id, controller_epoch, op_id)` and referring to a durable dispatcher-owned **host admission permit** scoped to one `logical_session_id`;
- the permit is created at the owner's admitted start with the session-host executor. The owner's **session lifecycle authorisation** explicitly authorises successors, if present, and is retained with the admitted input and session record; its member format is unpublished. A one-start request without it authorises no successor;
- every physical start keeps its own `(execution_id, controller_epoch, op_id)` claim, fence and same-effect/root-receipt interlock. The approved runner, unchanged canonical plan digest and active account generation remain part of the admitted launch path;
- `host_stop` in `dispatch-op/1` (R-SESSION) is accepted only from the configured session-host principal and only for an execution under its permit. It uses the dispatcher's journaled E-stop path (`exec.stop`, confirmed absence), records the stop as host-requested, is distinct from owner `cancel`, and confers no start authority;
- admission reserves host-owned producer and aggregate storage capacity and the protected control/evidence headroom (§3.1); replacements retain old debt, and aggregate exhaustion refuses new work without spending that reserve or creating an unbounded refusal log;
- identities kept distinct: account generation, execution identity and the backend's controller epoch;
- the interactive and resume subset negotiated explicitly (dispatcher slice 0 refuses them);
- negative qualification cases: wrong principal, wrong session or execution, replay, one-start request used for a successor, retired owner, revoked/expired chain, altered plan or executor, withdrawn/unresolved permit, prior claim not absent, cancelled claim, ambiguous start, host failure and crash on each acknowledgement.

**Successor admission (F-20/R-SESSION).** Only the owner's session lifecycle authorisation admits a successor `host_start`, idempotent per `(logical_session_id, op_id)`: replay returns the same successor, never a second. The previous claim must be confirmed absent first. Each use keeps the same allocation and generation and reuses the stored plan verbatim; the host supplies no plan bytes. Pin or posture divergence needs a new owner admission. The original owner must remain active, its chain unrevoked and unexpired; each authority-creating use passes fresh delayed-work checks and `revocation.check` with context `start`, with distinct effect IDs. A retired one-shot orchestrator's sessions are not restartable. The host acquires no caller chain, spawn grant or lease grant; the binding retains the original owner's caller dependency and ancestry. Successors stay within the owner's grant window and allocation lifetime. For ordinary work the authorisation has a cumulative or first-start-anchored restart budget, so successors cannot reset runtime windows; standing executions retain their no-runtime-limit rule. The budget format remains unpublished (§7).

The host prepares durable session intent and a closed delivery fence before `host_start`. Only the dispatcher invokes `swarma-user-launcher`, through its existing claim, effect and root-receipt path. The session-scoped permit spans physical starts, with the per-start fence interlock. A fence change withdraws the affected start's authority or sends it to reconciliation; unknown permit state keeps successors closed. Owner `cancel` or `retire`, chain revocation or expiry, the operator's signed standing-retirement record, and R-MAINT withdraw the permit durably and serialise with successor admission under the dispatcher's state lock. R-ALLSTOP durably suspends lifecycle authority and serialises with successor admission; its explicit recovery names the stopped set and per-session restart scope and still requires valid owner lifecycle authority or fresh owner admission. No autonomous repeat follows withdrawal or suspension. Controller-only re-adoption retains `execution_id` and needs no permit action.

Cancellation before the privileged call prevents the call; after an ambiguous call the dispatcher resolves the same effect and receipt and stops the execution if required, never launching twice. Host failure keeps the dispatcher claim and closed fence until reconciliation. Current-epoch runner registration and readiness precede delivery (§3.2–3.5). These semantics refine F-4; joint publication and qualification remain §7 question 2.

**Dispatcher controls while admission is closed (F-15).** The dispatcher is an unprivileged Unix-socket service from its first protected-launch slice (F-5), using broker §4.1 and §13 connection/framing rules. The host verifies server identity and authenticates as its configured service principal; the dispatcher verifies caller identity, active generation where applicable and request signatures. After exclusive state ownership, schema compatibility, journal replay and valid authentication/indexes, authorised status, list, observation, reconcile and already-authorised current-execution-bound stop remain reachable even when forward admission is closed. Observation of an old effect needs no new launch grant. An absent dispatcher has no command fallback; unusable shared state cannot be bypassed.

Before forward admission every non-terminal record is classified. Unresolved records retain their generations, allocations and quota/capacity claims; forward actions on them remain closed. Unrelated work is admissible only with complete accounting and proof that possible unresolved effects are confined to those retained claims and identities. If affected identities, accounting, shared authorisation or shared-state integrity cannot be bounded, forward admission stays closed node-wide. Maintenance, restore fencing and the existing fail-closed hold gate remain global barriers. No claim is released on unknown evidence, and no live supervisor is adopted. The operation-availability matrix and confinement proof are owned by the dispatcher (§§7–9, 11); this host adds no alternate launch path. Queueing, events, long waits and advanced integrations remain later capabilities on the same transport.

D-WIRE-NAMES naming and classification follow the [shared naming owner](https://github.com/relux-works/wiki/blob/main/naming.md#swarma-platform-technical-names). Signed domains such as `swarma-dispatcher request/1`, `swarma-credential-broker grant/1` and `swarma-credential-broker revocation/1` are distinct from transport/schema labels: the dispatcher retains `dispatch-op/1`, `dispatch-result/1`, `input/1`, `agent/1` and `run/1`, and the broker retains `broker/1`. A prefixed result-kind discriminator such as `swarma-dispatcher workspace-result/1` does not rename those labels or define their signing domains. No blanket prefix rewrite is authorised. The shared owner must publish the one-sentence scope clarification and typed owner-linked rule/wire index before the relevant freeze; this host consumes that index rather than defining another register (§7). Naming supplies neither missing signature grammar nor activation; user-manager v0/v1 use dispatcher-to-root caller/role policy, and caller-bound grant verification is a v2 gate.

D-PATH fixes the launch-scoped PATH in the digested plan: (1) this launch's protected tool directory (CIP-0007); (2) the admitted base PATH in its existing order; (3) one protected manager dispatcher directory, through which project commands run after checks. A repository `.agents/bin` MUST NOT be executed in a managed launch. The resolved PATH is recorded in the plan and covered by its digest.

### 3.4 Effects, fences and admission

Figures: [M-SH3 approval and receipt states](../diagrams/approval-receipt-states.puml)
and [M-SH4 storage ownership](../diagrams/storage-layout.puml) distinguish durable
evidence, unresolved outcomes and refusal. State labels illustrate the prose;
they do not publish the pending wire/state schema.

- **Effect matrix.** Every effect — enqueue, deliver, steer, interrupt, goal and control calls, attach, start, wake, retry, probe, session runner re-adoption — has its fence and epoch rule and idempotent `op_id` behaviour. A closed fence may queue but not deliver; only the operation holding the fence may restart; an explicit stop stays stopped; after a controller failure nothing writes to session runners before reconciliation.
- **One node admission authority** relates the dispatcher's capacity and execution claims, the host's fences and the session-scoped host admission permit and each physical start’s claim/fence held through start, with reconciled authority for verified re-adoption. Every starter is inventoried (board runners, manual and alias launchers, restart and recovery consumers, probes, retries, fallback legs, mixed-version clients); an unsupported participant blocks shared mutation. A fence change withdraws the affected physical start’s authority or sends it to reconciliation; host failure retains the dispatcher claim and closed fence. Unknown permits stay owned; unreadable state is closed; ordinary restart closure is separate from an operator's update lock, which only the operator clears.

**Wait/lock rule (F-28/R-LOCK).** The host MUST **never hold its state lock across a synchronous call to another platform service**. This includes its fence lock across `host_start`, `host_stop`, permit withdrawal/reconciliation and runner calls. Under the state lock it journals immutable intent and a durable per-record in-flight marker, then releases the lock, calls the receiver, and reacquires the lock to record/revalidate the result. Ownership is serialised by that marker, not by holding the global lock across I/O. The effect identity, canonical arguments and caller provenance are fixed at intent; authority is freshly checked at authority-creating uses, never cached from a prior verdict.

Each call is bound to its record and current daemon-instance/controller epochs without assuming a new wire member. Late results are revalidated against current fences and versions: stale results may resolve historical evidence, but never reopen delivery/admission or resurrect cancelled starts. Cancellation before issue prevents the call; cancellation or fence withdrawal during a call records intent promptly and observes the in-flight marker, so the post-call handler stops rather than proceeds. The host releases the fence lock before sending withdrawal to the dispatcher; the dispatcher reconciles under its claim/receipt interlock. Claims for possibly executed work remain retained until confirmed absence. Outbound I/O and in-flight work are bounded per service and serialised per record, leaving unrelated records and authorised status/stop controls reachable. Bounds and marker schema would need publication (§7 question 2).

The host's wait/lock graph is [M-SH5](../diagrams/host-wait-lock.puml): state lock → local journal/record transition only; unlocked in-flight operation → dispatcher or runner call → unlocked result handler → state-lock revalidation. There is no state-lock-held edge to another service, so the lock-wait graph is acyclic even though host and runner calls go both ways. Singleton/process-ownership locks have different lifetimes and are exempt; the rule does not release R-FD3/root generation exclusion or refresh-writer ownership. Qualification would need slow dependency with concurrent status/stop, mid-call fence withdrawal, cancellation and stale completion after replacement.

**Envelope replay binding (SH2+ target, schema pending).** Retain `(principal, id)` as the claim key. Store and compare the existing `envelope_digest` of the complete canonical signed content, excluding the signature value and bridge-authored wrapper, before enqueue, deduplication or returning a receipt. The immutable binding follows the bridge admission through host enqueue and receipt lookup. An exact canonical-byte retry returns the original receipt; any changed signed content under the same principal/id conflicts and requires a new ID, even if the body is unchanged. The digest MUST NOT be added to the claim key to admit changed intent as a new operation. This comparison does not waive separate authority, expiry, reconciliation or retention checks. Qualification must cover an exact-byte retry and identical-body changes to action, logical session, execution, media type, validity window, grants and binding revision; canonical coverage, ordering and conflict/receipt schema remain publication gates (§7.19).

**Storage and evidence (SH2+ target).** A closed-fence queue remains within its producer byte/count budget; admission/receipt writes reserve and charge durable capacity before acknowledgement (§3.1). Disposable diagnostics are separate from application/replay evidence. Safe retention/compaction must preserve required transcript, audit, claim and tombstone floors and retained debt until authorised disposition. Required evidence MUST NOT be deleted to make room; a truncated transcript is not intact, missing evidence is not confirmed absence, and unknown approvals/controls are never replayed. Incomplete evidence retains the closed/unknown state. The hard reserve protects against producer exhaustion, not arbitrary corruption or a dead filesystem, which remain storage failures (§7.20).

**Receipts and approvals (SH2+ target, schema pending).** Delivery records distinguish `accepted`, `queued`, `dispatched`, `applied`, `refused`, `expired` and `unknown`; no acknowledgement is emitted without a durable write. After a host or runner failure between dispatch and application, reconcile the input marker against an intact transcript before reopening the fence. A matching marker proves applied; confirmed absence in an intact transcript permits redelivery; unresolved evidence stays unknown. An unknown approval answer or control effect MUST NOT be replayed automatically. Historical approvals become invalid on restart.

A pending native interaction binds its execution, turn, native request digest, options and expiry. An authorised approval must target that pending interaction and the current execution/epoch, match the digest and remain unexpired. Compare-and-swap accepts the first valid resolution; an ordinary user turn is not an approval. Closing the fence invalidates pending interactions. Automatic approval requires an explicit allowlist policy. These are [architecture receipt and interaction requirements](https://github.com/relux-works/wiki/blob/2e30edbd54977b306ab53497663fcd94a5ca6cb6/session-host/architecture.ru.md#L376) to carry into a dedicated module wire/state schema before activation, not a claim that SH1 implements them; this revision invents no wire fields or policy values for that schema.

### 3.5 Park, restart, emergency stop, board completion

Figures: [M-SH2 recovery sequence](../diagrams/session-recovery.puml) and
[M-SH3 independent lifecycle views](../diagrams/session-goal-wake-states.puml)
keep controller recovery, execution absence, park and optional board completion
separate. The [workspace transfer and verification](../diagrams/workspace-transfer.puml) and [node-wide emergency stop](../diagrams/node-emergency-stop.puml) views show the distinct board and node operations.

- **Standing-session eligibility and lifetime (R-STANDING; owner decisions, 2026-10-12/13).** Standing host sessions require trusted class AND local agent placement with admitted launch authority; trusted-circle membership alone is insufficient. Every remote placement is a workplace whose loop runs at the donor, never a host session (§3.1). A standing session held by the host MUST have no preset lifetime or runtime limit, and its executions MUST have no preset runtime maximum. It ends only by an explicit stop, by operator action (including emergency stop), or by its own exit. Park and restart MUST NOT end the standing session: park holds delivery closed, while controlled restart replaces an execution within the same session. The dispatcher's 12-hour maximum execution runtime (§3.5 of its specification) applies only to non-standing executions. This decision supersedes R3; it does not activate the SH2+ backend or publish a runtime-policy wire format.
- **Operator maintenance (R-MAINT, dispatcher §11).** Standing sessions participate in the dispatcher's bounded maintenance attempt: close new admission, inventory existing executions, then stop selected executions with explicit operator authority through the dispatcher and `exec.stop`. Confirmed process absence and reconciliation are required before any change of mode, mutable-state migration or binary swap. The maintenance deadline bounds the attempt, never the session's or standing execution's lifetime. Unknown or refused stop, or incomplete reconciliation, defers maintenance. Standing allocations and identities remain; there is no live dispatcher adoption or automatic expiry. Host controller-only re-adoption (§3.2) is a separate recovery operation. R-MAINT withdraws lifecycle authority; any intended restart remains subject to operator review and fresh owner admission with an admitted plan/transport. Recovery controls remain reachable while forward admission is closed (F-15, §3.3); unsupported rows stay visibly stopped.
- **Park** is a durable host operation that holds delivery closed. If a board goal is bound, the optional board client acknowledges a committed goal revision carrying the handoff reference (compare-and-swap); that board barrier is not a prerequisite for a goal-free session. The note attempt is bounded, with an explicitly marked snapshot fallback; a timeout never proves drain. For a wedged execution, the host requests `host_stop` under its permit and retains the fence and claims until confirmed absence; that stop grants no successor authority. The goal-free park receipt/state schema must be published before activation (§7).
- **Restart** follows the architecture's transaction under a closed delivery fence: drain external effects and child tools, request `host_stop` from the dispatcher under the session-scoped permit, through its journaled E-stop path and the user manager’s `exec.stop`, confirm process absence, check binding, posture, authentication, grants and runtime, then request a successor execution and fresh agent-side runner through `host_start`, solely under the owner’s session lifecycle authorisation and session-scoped host admission permit (§3.3). `exec.stop` follows the single termination scope in the user manager’s §§4.4 and 4.7 (F-13): while one execution per generation holds, it signals every process of the generation’s UID (TERM, grace period, KILL), stops its per-user service domain where present, and verifies account-wide absence over a quiet period. Receipt/process identity authorises the target; it does not limit the signalled set to one process session or a wall-clock receipt window. Account-wide signalling requires the generation’s latest execution receipt; a successful stop replays without signalling, and an old receipt never stops a later execution. Future concurrent executions would need exact per-execution containment before activation. The stop is harness-agnostic and proves process absence only; unkillable processes remain unknown. Runner fate and the affected set on service replacement follow R-FATE (§3.2), never deployment defaults. The fresh runner checks the harness's native-session lock under the closed fence and reports the result to the host before harness initialisation or native resume. Only confirmed native-lock absence permits that step; an unknown result keeps the session parked with delivery closed. Then initialise or resume, reconcile unknown delivery and reopen only after current-epoch registration, readiness and reconciliation. The host does not signal the processes directly. Unknown process evidence cannot release capacity or authorise replacement.
- **Harness surfaces (R-STANDING).** Settings, hooks, MCP configuration and instruction files of trusted standing agents come from the plan. The executor MUST verify their digests before **every launch, restart and native resume**, or supply them from a root-owned location outside the home. Drift refuses the launch and is reported; its refusal code is unpublished. Repair is explicit re-materialization, never silent acceptance (§7.15). Native-lock absence and semver compatibility do not replace this check.
- **Native resume (D-RESUME/R-STANDING).** After the harness-surface check above, on the same machine, a non-breaking harness semver change is allowed without an extra qualification row: the same major, and for 0.x the same minor. A different major or 0.x minor MUST be refused. Keep the same runtime family, managed home (checkout × profile × environment), profile pin and intact transcript digest, exclusive native-session lock, ready authentication and current grants. Preserve the admitted transport (`tty` with PTY preservation, or `hosted-stream:<adapter>`); no transport conversion is inferred. If the harness fails native resume, report `resume-failed` to the caller and let the caller decide the next action. There is no automatic fallback machinery, and portable seed is not part of this resume path. A per-harness note records vendors known not to follow semver. This replaces the unresolved version choice in contract row P8; SH1 extraction itself still preserves existing behavior.
- **Recovery matrix:** provider × owner kind (primary, owner-run) × source record (hosted, legacy) × recovery mode, each row with its fresh plan and credential supply, authority, home and native identity and readiness checks; unsupported rows stay visibly parked or refused; legacy ambient environments are never replayed into the new account.
- **Board completion**, when an optional board client is bound, is a separate barrier: an execution's exit never satisfies the board's `wait`; exit receipts are durable and replayable.
- **Session emergency stop (R-SESSION/R-OPERATOR):** an operator command with defined scope and authority closes delivery, snapshots any bound board and requests `host_stop` under the session permit through the journaled E-stop path. Keep fences and claims until confirmed absence, record receipts and recover only explicitly. It is host-requested, distinct from owner `cancel`, and confers no start authority. Sessions without a board do not require a board snapshot.
- **Node-wide emergency stop (R-ALLSTOP).** One operator narrowing act, refused from inside agent sessions, uses the phone path with authentication and one confirmation, or the terminal fallback. R-OPERATOR keeps custody in the separate `swarma-operator` account (never a harness host); phone acts are signed over exact canonical content by the presence-gated hardware-backed **operator device key**, via tailnet SSH with key-only login and a forced narrow **operator command**, no shell. The app shows the exact act content before signing; the machine checks against the pinned phone key, binding the signature to that one act’s canonical bytes so it cannot be reused. The fallback is password `sudo` into that account, no `NOPASSWD` or cached ticket (`timestamp_timeout=0`); read-only status uses `swarma-observer`. The operator command fans the same signed act, act identity and canonical bytes directly to each service’s operator intake; each verifies and journals its own part idempotently without waiting for another service. It reports per-service results and retries undeliverable parts, which remain unknown. The dispatcher sets hold at act admission without waiting behind fan-out calls; no offline writer of dispatcher state is authorised. Broker lease/renewal freeze, user-manager range deny-all and **host delivery closure for every session** are issued promptly and independently; process stops start with bounded parallelism without waiting for containment replies. Already-delivered tokens keep their vendor lifetime. The user manager persists the root-owned all-stop mark before scanning: it fences physical launches, including materializers/exporters and already-issued calls, as well as creation and activation, through the inventory/absence frontier. It journals account-wide stops initiated by the dispatcher when available, or by the operator helper path when unavailable; the terminal path exists, while the phone-to-helper transition needs publication. The dispatcher later reconciles operator-stopped evidence, releasing claims only on confirmed absence and never relaunching. The host journals closure, invalidates pending interactions, snapshots bound boards and records session closure while the dispatcher durably suspends session permits; it keeps fences while absence or another required part is unknown. Cuts and stops can progress during dispatcher absence, crash loops or maintenance, but whole-act success and recovery require every durable service part, including the dispatcher’s reconciliation. An empty process scan without the receiver fence is insufficient. A broker freeze reply may remain unknown while helper stops progress; admission stays closed. Recovery is an explicit content-confirmed act naming the stopped set and per-session restart scope; valid owner authority or fresh admission is still required and no restart is automatic. Clearing one closure condition never clears the other independent gates. Dispatcher-unavailable progress and never-launched-generation coverage remain distinct acceptance cases (§7.16). Act/record formats and the operator command binary/format, signature domain and canonical bytes remain unpublished (§7.16).
- **Candidate, rework and verification (R-TRANSFER/R-VERIFY).** The board accepts exported results only as resources. Its change-request machinery owns deterministic import, candidate, exact-commit review and integration; the orchestrator executes them, never the host. The import creates C on admitted B in a scratch index with hooks and attribute filters/drivers disabled, refuses `.git` components, out-of-write-scope changes and every `.task-board/` change, and requires explicit hunk-by-hunk verdict acknowledgement for the R-TRANSFER flagged CI, Git behaviour, hooks/auto-run, agent instruction/configuration paths and every symlink. C is signed by the repository identity with worker/run/result-digest trailers; its tree equals recomputation from B plus the change set. Review admission requires a positive review-role grant, never derived from class or circle membership: the reviewer is a trusted-class local agent placement or a person holding the review role, outside the untrusted class and distinct from the producing identity, and reviews exactly C. Circle membership alone never grants review authority. Optional local-only reviewer and requester-exclusion policies remain unchosen and off (§7.21). K1 acceptance binds to C, never patch equality; untrusted candidates are never pushed to secret-bearing CI before acceptance. Worker accounts never push or open merge requests. A changes-requested verdict starts rework on base C with the reviewer’s findings in the local agent’s **task snapshot**; this is a new admitted run, not an unchanged-plan R-SESSION restart. Remote rework uses a signed task letter, continues the donor-side session and re-materializes from C, removing the prior workspace only after recorded export. The next export yields C2 on C; questions use ordinary letters/outcomes, and intermediate export uses the same fence at a turn boundary. Accepted exact heads land only by the board’s signed fast-forward path (K1/K3); moved bases use ordinary refresh and re-review. The deterministic import command is unpublished (§7.13). The flagged paths are: `.github/**`, `.gitlab-ci.yml`, `.circleci/**`; `.gitattributes`, `.gitmodules`; `.githooks/**`, `.husky/**`, `.pre-commit-config.yaml`, `lefthook.yml`, `.envrc`, `.vscode/**`; `AGENTS.md` and `CLAUDE.md` in any directory, `.claude/**`, `.codex/**`, `.agents/**`, `.mcp.json`; and every symlink. RWP v2.1 §8/§10 transfer gates are adopted; export is by the approved child-UID executor rather than harness access to a container volume.
- **Candidate consumption (R-TRANSFER; CIP-0002).** Every agent consuming an unaccepted C, including reviewer, orchestrator and tester, reads its files as untrusted data, never automatically adopted instructions, hooks, MCP servers, permissions, skills or executable discovery. This holds at startup, reload, nested discovery, resume and child entry, before and after flagged-hunk acknowledgement. The first review path presents exact-C diffs/blobs as read-only, digest-bound inert task resources (R-NET-TOOL 4a) outside harness discovery roots. Materializing or entering C in a discovery-capable harness requires a qualified strict-context adapter (CIP-0002 strict mode or equivalent ambient-discovery exclusion) as a launch admission gate; an unqualified harness tuple cannot host that path. Root-supplied surfaces alone are insufficient without ambient-discovery exclusion. The verdict must record every flagged hunk and show that no automatic load preceded acknowledgement; the inert path establishes that ordering by construction. Acceptance of C is not admission of its control surfaces: activating them requires a separate control-context decision. Data-only review still requires scrutiny of semantic prompt injection. Qualification on each supported harness’s real tool path must exercise candidate hooks, MCP entries, instruction files and skills at launch, reload, nested read, resume and child entry, with no load/execution and all flagged hunks recorded (§7.22). This is a required first consumer of strict adapters, not a claim of full CIP-0002 rollout.
- **Verification phase (R-VERIFY).** All candidate builds/tests/generators and any execution of worker-produced code run only in isolated ephemeral runners on a machine other than the agents’ host, without secrets, with controlled dependency egress per R-NET-TOOL. Results return as data to the board’s testing state. A tester role orchestrates and reads results; it never executes the code itself. Runner pool, job contract and result format belong to board/infrastructure lanes and are unpublished (§7.17).

### 3.7 Wake and liveness

No hosted agent re-arms its own wake-up; there is no `wait` for the model to forget.

| Responsibility | Owner |
|---|---|
| receive mail for an agent identity and hold it durably | the bridge (carrier provider and Mailbox); it enqueues into the host's per-session inbox and counts delivery only after the host's durable write |
| decide when to deliver (the doorbell) | the host, the only writer of a session's input; it delivers at a turn boundary |
| report the turn boundary, idleness and heartbeats | the session runner (§3.2), through the adapter's readiness grammar: Claude PTY or stream output, Codex app-server turn events; an unknown readiness parks rather than guesses |
| detect a wedged session | the host: pending inbox items, and the session neither idle nor progressing past its deadline |
| recover | the host's restart transaction (§3.5) under a new controller epoch: `host_stop`, confirmed prior-claim absence, then successor `host_start` only under the owner’s session lifecycle authorisation and session-scoped permit, then redelivery under the immutable principal/id-to-complete-intent binding (§3.4); the dispatcher for admitted starts, execution stop, absence and cleanup (§3.2–3.5) |
| never woken | an explicitly stopped or parked session, a closed fence (it queues, it does not deliver), a session that needs re-authentication (parked); queue acceptance still obeys byte/count budgets |

A wake is an effect in the §3.4 matrix: fenced, epoch-checked, with an idempotent `op_id`. The binding from an agent identity to a session names the session, the execution and the epoch, so a wake after a restart never reaches a stale session. Claude Code and Codex are covered; Muse after its qualification (§3.6).

Liveness deadlines use monotonic elapsed time within a boot; after reboot unknown elapsed evidence cannot justify a guessed deadline. They detect a wedge; they MUST NOT impose a lifetime or runtime limit on a standing session. Recovery by park or controlled restart preserves that session (§3.5); only an explicit stop, operator action or its own exit ends it. Time confidence follows R-TIME (§3.1); a clock step cannot revive authority or turn wedge detection into expiry-driven destruction. Maintenance uses R-MAINT (§3.5); its deadline bounds the attempt, with recovery controls reachable while forward admission is closed (F-15, §3.3).

**Producer storage pressure (SH2+).** Closed-fence mail and sustained runner output obey §3.1 budgets even while a standing session has no preset lifetime. Bounded backpressure/refusal or journaled park/stop must occur before producer exhaustion reaches the protected reserve, including when the runner does not cooperate (§3.2). Agent-home watcher telemetry is not host retained-byte accounting. Budget pressure may narrow the affected session; replacement, retirement and recovery neither release retained evidence debt nor imply evidence absence (§3.4). Before SH2 activation, qualification must demonstrate sustained output and closed-fence queues at boundaries, producer/aggregate limits across replacement/retirement, claim-retention floors, required stop/park/fence/recovery space for both affected and unrelated sessions, and bounded refusal behavior at aggregate exhaustion (§7.20).

**Usage watcher (R-WATCH).** This is separate from wake/liveness detection. Per-UID telemetry covers CPU, memory, process count, home disk, network counters and refused connections including mail ports. The sampler is read-only with least OS-required privilege, root only where required and no other authority; thresholds are per admission class. A sample used for automatic narrowing must bind the observed generation, boot and sampling interval, revalidated under a stable current ledger view before action. Baselines never cross generations/boots; stale, unknown-reuse or unverifiable samples are discarded, never retargeted. **v0 scope:** a hard-threshold crossing requests a journaled dispatcher `exec.stop` for that account only and retains the affected session’s closed delivery/admission hold; it offers no per-account egress-freeze guarantee and no token retraction. Node-wide range deny-all is not its substitute. The host records the stop reason durably and parks or ends the session, retaining fences/claims while absence is unknown; no automatic restart is permitted. **v0 alerts are status-only:** the operator learns of watcher conditions through authenticated `swarma-observer` status reads. No phone delivery is promised. Containment and stop progress never wait for alert delivery. An enabled later alert lane would need an owning principal, qualified route, bounded durable delivery/status and retry/unavailability semantics, closed typed content without agent-controlled strings and rate/storage bounds. Notification carries no operator-act authority and adds no host egress permission. The full per-account freeze lifecycle is v1 publication work with the enforced-network contract package (§7.18), not specified or activated here; node-wide stop stays manual (R-ALLSTOP).

Until SH2+ is active, interim rails live outside this module: a per-identity watcher that holds the wait itself and injects one fixed line only into an idle session with an empty input line and never into one the operator stopped; and, for sessions in today's daemon, its notice path, which delivers only while a client is attached (§1.1).

### 3.8 Goals across accounts

Figures: [M-SH1 cross-account components](../diagrams/components.puml) and
[M-SH3 goal command/acknowledgement view](../diagrams/session-goal-wake-states.puml)
show caller authorship, optional board ownership and host-to-runner delivery.

**D-GOALS: variant (b) now.** Only the board/orchestrator for board goals, or the launching caller at start through the launcher, sets a session's goal. The agent account has no goal capability on the host socket. This keeps goal-authoring authority with the initiating caller while the separate agent namespace and its bounds await SH2+ design.

The goal interface is generic and optional. The host MUST work without a board, goals, our orchestrator or its toolchain; goal absence MUST NOT block launch, attach, delivery, wake, stop or recovery. The board's ledger, ancestry, outcome proposals and completion barrier belong to its optional adapter (§2.2–2.3), not to the host's session lifecycle. SH1 retains today's board adapter behavior through its compatibility seam; it does not make that adapter a mandatory dependency of the extracted module.

**Unspecified goal surfaces (§7).** The goal-client interface on the host socket, including its actions and capability shape, is unpublished; the flow below states authority and ordering, not an API. The source of a per-session nudge or wake budget, who sets it and the default when no board is bound are unspecified. There is no specified path for an agent to propose "done" when no board is bound. With a board, an agent outcome is only a proposal to the board owner. D-GOALS gives the agent account no goal capability: any future proposal path MUST NOT mutate a goal.

When a goal is present, the authoring caller, the host and the agent run under separate accounts. The optional board client runs under the orchestrator's account or its service account; the host under `swarma-session-host`; the runner and harness under `worker-<label>`. The SH2+ flow is:

1. An authorised launching caller passes an initial goal through the launcher, or the orchestrator sets or updates a board goal through the optional board binding.
2. The initiating caller's goal client asks the host to apply revision N to session S. The board binding is one such client. The host identifies the caller by kernel peer credentials (UID and active generation) and requires its session-scoped capability with the applicable goal actions, audience, expiry and revocation. S's fence must be open. An agent-side executor carrying a caller-composed plan acquires no goal-authoring capability.
3. The host records the revision durably. At the next turn boundary it hands the revision to the runner of the current epoch, which writes it into the harness input (§3.2, §3.7) and returns the harness's acknowledgement.
4. The host answers that client: applied, deferred, or rolled back with the joined error, as in today's goal seam. The optional board adapter keeps its ledger transaction and exact-revision acknowledgement semantics.

The runner accepts input only from the host. Its fresh authenticated channel and registration must establish that it belongs to S's admitted execution in the current controller epoch before readiness and delivery; the host talks only to that registered runner. The proof format remains unpublished (§7 question 2). Revoking the initiating principal's grant or session capability stops its goal operations at once; stopping the execution stays with the dispatcher through the user manager's `exec.stop`.

**Deferred SH2+ item (G2).** The final choice is (a) agent self-goals in a separate namespace, with its authority and bounds designed separately, or (b) retaining caller/board authorship only. No agent self-goal API is enabled now. Agent-reported board outcomes remain proposals to the board owner, not agent-authored changes to a board goal. This later choice does not block the goal-free host.

In SH2+ the module also ships the host service binary, and the optional board client uses this socket instead of compiling the session manager in.
